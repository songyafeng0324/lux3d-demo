# 首屏下载量验证（藏宝阁首页 `/`）

> 2026-11-12 · Mac 本机 · Chrome 157（Playwright 无头）· 生产构建 `apps/web/dist` · 未部署到线上

## 目的

香港服务器到大陆访客的跨境速度波动很大，13 MB 的 GLB 下载用时从 0.95 秒到 80 秒不等。用户第一次打开首页用了 43 秒。大陆 CDN 需要备案，暂时用不了，所以要缩小「进入藏宝阁」出现之前必须下载的数据量。目标是首屏 ≤ 8 MB。

## 测量方法

用 [`scripts/first-screen-bytes.mjs`](../../scripts/first-screen-bytes.mjs)：

- 本机临时静态服务读取打包产物，压缩方式与线上 Nginx 一致：除 PNG、JPEG、WebP 外都用 gzip 1 级。线上实测 GLB、KTX2、JS、wasm 都带 `content-encoding: gzip`，PNG 不压缩。
- `/api` 一律返回 404，不连数据库，所以展陈读取失败、展品数为 0。
- 用浏览器的 Resource Timing 按请求开始的时间分成三段：进场画面出现前（首屏）、进场画面显示期间、点击进入之后。字节数取 `transferSize`，即实际传输量。
- `--throttle-mbps=5` 用 Chrome 网络模拟限速到 5 Mbit/s、加 60 ms 延迟，看用户实际等待多久。
- 改动前的数据来自 `git archive HEAD` 重新构建的旧产物，文件哈希与改动前的构建一致。旧版所有请求都在进场画面之前发出，所以按开始时间还是按完成时间分段，结果一样。

## 结果

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 首屏传输量（gzip 后） | **22.55 MB**（47 个请求） | **3.55 MB**（45 个请求） |
| 首屏原始大小 | 25.92 MB | 5.92 MB |
| 5 Mbit/s 下进场画面出现 | **36.8 s** | **6.4 s** |
| 5 Mbit/s 下角色出现 | 与进场同时（36.8 s） | 9.7 s |
| 5 Mbit/s 下原尺寸贴图全部换完 | 与进场同时（36.8 s） | 35.4 s（这时访客早已在走动） |
| 全部内容合计 | 22.55 MB | 21.38 MB |

全部内容的总量基本不变，只是调整了先后顺序；节省的 1.2 MB 来自天空图改成 WebP。线上 `/assets/` 带一年缓存，再次访问时这些文件都直接读缓存。

改动后首屏的主要内容（传输量）：

- 建筑 GLB 2.11 MB：几何体，加上 56 张 128 px 预览贴图（共 0.27 MB）。
- 34 张 256 px 预览光照贴图约 0.42 MB。
- basis 转码器 0.28 MB，各个 JS 约 0.4 MB。
- 天空图 WebP 0.32 MB（原来两张 PNG 共 2.11 MB）。

数据文件：[before.json](evidence/first-screen/before.json)、[after.json](evidence/first-screen/after.json)、[before-5mbps.json](evidence/first-screen/before-5mbps.json)、[after-5mbps.json](evidence/first-screen/after-5mbps.json)。

## 改了什么

1. **贴图分两级**（[`compress-t16.mjs`](../../scripts/compress-t16.mjs)，按 T16 规则重新生成 `assets/t16/runtime/`）：
   - GLB 内只放 128 px 的 ETC1S 预览，每张的名称唯一。原尺寸 KTX2（编码与原来相同：颜色和粗糙度 ETC1S，法线 UASTC）放在 `runtime/textures/`。
   - 每张光照贴图另有一张 256 px 的 `-preview` 小图。
   - `manifest.json` 记录了每个文件的哈希。单元测试检查以下几点：预览名称唯一；每张预览都有对应的原尺寸文件；哈希一致；GLB 内的预览总量小于 600 KB；GLB 小于 5 MB。
   - 几何体、行走数据和光照贴图原图都没有改，原尺寸光照贴图与改动前逐字节相同。
2. **引擎先显示，再换清晰贴图**（[`engine.ts`](../../apps/web/src/game/engine.ts) 的 `loadDetail`）：进场画面出现后，用同一个材质的同一个槽位换上原尺寸贴图。UV 和颜色空间不变，所以不用重新编译着色器。
   - 先换光照贴图和颜色贴图，法线贴图最后换，同时下载 4 个。
   - 某张下载失败就保留预览。
   - 全部换完后重新拍一次反射探针。
3. **角色延后**：选中的角色原本和建筑一起下载（约 2 MB），现在等进场画面出现后再下载，而且先单独下载角色，再开始下载原尺寸贴图。
   - 任务说明里说 6 个角色都会下载，实测不是这样：改动前就只下载当前选中的一个，其他角色要打开选角框选中后才下载。
4. **展品在点击进入后才加载**：每加载完一件，就挑离访客当前位置最近的下一件，同一时间最多 3 件。展陈 JSON（很小）仍然在进场画面出现时读取。
5. **天空图改为 WebP**：[`prep-t16-sky.mjs`](../../scripts/prep-t16-sky.mjs) 用 sharp 直接从原画 A11、A12 生成，替代 Blender 脚本 `prep_t16_sky.py` 和两张 PNG。大小从 2.11 MB 降到 0.32 MB，透明边缘保留。
6. **修了加载进度条**：原来进度按 `Content-Length` 计算，但线上 Nginx 用 gzip 传 GLB 时没有这个头，所以进度条一直停在 0%。现在按 manifest 里记录的文件大小计算。
7. **加载提示**：进场画面显示「高清贴图载入中 · n%（可以先进入）」，进入后页脚显示「高清贴图 n%」，换完后消失。

## 展品详情不再重复下载（同日追加）

- **现象**：线上在展品前按 E，弹窗里「正在载入模型…」要半分钟以上。
- **原因**：详情预览没有用场景里已经加载好的模型，而是带着 `cache: 'no-store'` 把展品文件重新下载一遍。线上 10 件展品每件传输 8–14 MB，从本机下载一件要 20–43 s。
- **改法**：引擎按模型文件 id 记住当前展陈版本里已解析的展品（加载完成或正在加载的都算），`borrowExhibit` 返回一份共用几何体、材质和贴图的副本（`SkeletonUtils.clone`）。`ModelPreview` 新增 `borrow` 参数：借到的副本立即显示，关闭时不释放共用资源；借不到或失败时，照原来的方式下载。展品还在加载时，预览等它加载完，不会再下载一份。
- **验证**：
  - `test:t15` 新增断言：从按 E 到预览出现，不得请求 `/api/v1/files/`。实测预览 112 ms 出现，重复请求 0 次。
  - 连续开、关详情两次后回到展品前截图，场景里的展品与打开前一致，页面没有报错。
  - `test:t08` 8 步全部通过，`npm test` 128 项全部通过。

## 已知限制与后续

- 慢网时，进入后的前几十秒里，近处贴图会从模糊逐渐变清晰。如果要缩短这段时间，可以把颜色预览提高到 256 px：首屏会多约 0.5 MB，5 Mbit/s 下进场画面晚约 0.8 s。这次没有采纳。
- 慢网下，展品和原尺寸贴图在进入后一起下载，会互相分带宽。
- 展品本身很大：线上 10 件合计约 115 MB 传输量。展品文件是 `private, no-store`，前端也用 `no-store` 请求，所以每次访问都要全部重新下载。小屋模型也一样，每次进入都要重新下载。建议合成一个独立任务，同时覆盖藏宝阁和小屋：入库时生成网页用的压缩副本；前端把模型存在浏览器本地，每次进入先问服务器还能不能看，能看才用本地那份，这样不破坏「撤销后立即失效」的权限规则。本次没有做。
- 未部署。部署由用户执行 `bash scripts/deploy-hk.sh`。部署后建议在大陆网络下实际打开一次首页，记录进场画面出现的时间。
- 另外发现：线上 `/three-basis/` 下的转码器文件名不带哈希，缓存头是 `max-age=0`。因为带了 `etag`，再次访问时浏览器只问一次「变了没有」，服务器回 304，不会重新下载这 0.28 MB；但这次往返正好卡在首屏的必经路上，每次大约多花零点几秒。建议改构建，让这两个文件也带哈希、放进 `/assets/`，这样直接套用一年缓存。不建议只在 Nginx 上加缓存：文件名固定，升级 three.js 后旧的转码器会和新代码对不上。本次未做。
