# T02 · 数据与接口契约 v0.1

日期：2026-11-04。适用：本地 MVP。领域语义为实施基线；供应商参数、几何尺寸、吞吐策略待 T03/T04，不在此猜测。API 尚未实现，本文中的请求响应是协议约定。

## 1. 通用协议

前缀 `/api/v1`，JSON UTF-8；上传 multipart。本站 UUID 作为字符串；供应商 bigint ID 全程十进制字符串。时间戳 UTC ISO8601，quota_day 用受理时 `Asia/Shanghai` 日期 YYYY-MM-DD，不能取浏览器时区。金额/次数不是浮点累计。

成功 `{data,requestId}`；列表 `{data:{items,nextCursor},requestId}`；错误 `{error:{code,message,fields?},requestId}`。401 未登录、403 权限/CSRF、404 不存在或非本人资源、409 版本/状态/请求键冲突、422 输入/配额/在途限制、503 服务未就绪。服务端日志关联 requestId，响应不含供方密钥、SQL 或私有路径。

所有业务写入携带 `Idempotency-Key`（用户+方法+路径+key 唯一，持久请求hash/结果）；同键同输入返回原结果，不同输入409。业务拒绝不占额度；成功任务及保存回执不得因短期缓存过期而可重复执行，结果保留到关联对象清理；登录/注销按自然幂等处理。身份/授权及当前资源撤销检查先于回放，不能靠旧回执取得已删除文件。

工程输入初值（非历史用户已选参数）：username NFKC 后 ASCII 字母数字下划线 3～32，大小写折叠唯一，显示原账号；nickname 1～40，password 12～128 字符不截断；房间名/资产名1～80、简介1～2000（个人简介可空），公共必填字段 trim 后非空；年代/材质接受“不详”，官网可空，非空为 http/https。输出文本按文本渲染。阈值若样本不适合，修改合同并同步用例，不改产品范围。上传体积/纹理/格式的策略由 E01 单独定稿。

同键并发协议：事务首先取得 actor/method/path/key 的事务级 advisory lock，再读取回执；已有回执且 body_hash 相同就返回原结果，随后才检查额度/baseVersion。所有写路由都先取得请求锁再拿业务行锁，不在业务锁内再拿另一个请求锁。请求摘要使用服务端带密钥摘要，回执不保存密码正文。同键等待者在前者提交后得到相同结果，不提前返回额度不足或版本冲突。

### 必需补充字段与导入记录

- files 另含 owner_id、purpose(input_image/model/original/derived)、state=staged/committed/deleted；上传落盘后才改committed并返回inputFileId。受理前验证本人所有、用途与committed态。
- rooms 另含 share_epoch、share_token_ciphertext；稳定token用持久 APP_DATA_KEY 加密保存，查询索引存hash。snapshot_grants 另含非秘密 UUID id，URL路径只用id，授权头传实际token，二者匹配验证。
- asset_imports：id/admin_id/input_file_id/source_type/metadata_snapshot/policy_version/state/result_asset_id/error_code，state=accepted/validating/succeeded/failed；与请求回执及唯一import job原子创建。结果资产按import_id唯一。
- provider_evidence：attempt_id/dispatch_nonce/provider_task_id/observed_at/evidence_hash，按attempt+evidence_hash去重。失租worker只可登记匹配nonce的关联证据，不可改业务终态；当前持租者核验ID后恢复对账，不能丢掉迟到ID。
- 后台导入成功事务一次性发布ready资产、文件关联、家具可用记录或官方candidate与active_publications占用，并标import成功；重放job不得重复发布。后台修改自录公共文字时更新candidate并生成新gallery版本，旧grant继续读旧资料。

public_snapshot={name,description,era,material,ownershipType,holderName,location,officialUrl?,sourceNickname}；ownershipType=personal_collection/museum，署名服务端取提交时昵称或官方馆藏，不能客户端伪造。其余必填字段按PRD校验，官网可空。

## 3. 事务与竞争处理

所有受保护写入在事务中重查权限与源资产状态。统一多对象锁序：涉及 users 按ID→assets 按ID→rooms 按ID→gallery 单例→任务/额度/申请等从属行；读取时先取 ID，再按此序锁定并重新核实。禁止删除按 asset→user、受理按user→asset这类相反顺序。队列领取在独立短事务内，只拿job锁后提交，不带job锁进入业务事务。[PostgreSQL 锁文档](https://www.postgresql.org/docs/18/explicit-locking.html)。

| 操作 | 原子边界 |
|---|---|
| 受理生成 | 锁user；ensure quota_day并锁；检查非终态/额度；新task、attempt、job、reserve事件、used_net+1、receipt同提交。上传失败不进入受理事务 |
| 生成成功 | 锁user及资产/任务；核对fence、非终态和文件committed；唯一建asset+result、task succeeded同提交；used_net不再加 |
| 最终失败 | 锁user/原日额度/task；条件非终态→failed；插唯一refund、used_net-1同提交；重放无副作用 |
| 当天调额 | 锁目标user及今天quota_day，仅override_total变；不改used_net，不终结任务 |
| 保存房间 | 锁user、请求与旧版关联资产并排序、room；校验版本/归属/ready/边界；新immutable room_version+room当前版本+receipt同提交 |
| 投稿 | 锁源asset；校验本人ready和active_publications不存在；新pending与占用同提交 |
| 审核/撤回 | 同样锁asset；pending条件更新；批准创建candidate、原子把占用从submission切到candidate；驳回/撤回删除占用。已处理再次请求409（原键回放原结果） |
| 发布展位 | 锁相关assets再锁gallery；校验候选可用；延迟candidate唯一约束或同事务先清后分配，按最终30槽校验；版本+slots+snapshot一次提交 |
| 风险删除 | 锁owner（若有）、asset、受影响rooms、gallery；重查引用集；清活动摆放并推进room版本、删除申请/候选占用/展位并推进gallery版本，asset tombstone、清理job、receipt同提交；保留其他模型；之后文件清理可重试 |

删除的引用集发现需要更多room锁时回滚并按序重试，不在持锁后逆序扩展；源asset锁阻止新的引用创建。所有加引用路径必须先锁asset，包括后台分配家具、审批、房间保存与文件就绪发布。失败/删除后晚到结果必须先检查状态，不重新建asset。

房间保存条件：body `baseVersion` 与当前一致，否则409 ROOM_VERSION_CONFLICT，返回 currentVersion，不回传全背包。重放写入先取receipt，确认body_hash再返回相同savedVersion；客户端只确认对应editSequence。存在后续编辑则仍显示未保存，不用旧版本覆盖。

## 5. 快照和文件权限

入场时服务端只签发当前发布/保存版本的 grant（随机256bit，服务器存摘要）；默认有效24小时，在线续期保持原快照，过期需要重进入。该时长是工程会话策略，可按测试调整，不是布局实时更新频率。分享grant保存 share_epoch，每次开关share推进epoch，关闭后旧grant不能借重开继续读文件；旧分享链接token始终相同，重进入获得新grant。

每次读新文件/详情/续期均核查：grant未过期、资源在其快照、share仍开启且epoch一致（若是room）、源asset未删除。普通移除/撤展不撤销grant中的原资源；关闭分享/风险删除使新请求拒绝。已加载浏览器画面不主动清空，不推送移除，不创建分享页详情接口。token传授权头，URL路径中的grant只用不含原token的标识，服务端仍校验header；日志脱敏。

房间分享DTO只含房名、主人当前昵称、固定壳体、已摆模型及变换；无背包、原图、个人任务、公共投稿资料。gallery DTO与详情锁定其获准版本，候选来源署名为提交时昵称或官方馆藏。

### 文件读取的完整权限和缓存协议

GET /files/:id/content 同时支持 U、A、G。U仅本人原图/模型及可用家具；A须由当前有效资产、申请或导入关系取得管理范围，可预览审核原图/模型，但不能任意枚举孤儿上传。G不包含原图。源资产删除后，包括原图在内的新请求均拒绝；未被资产引用的输入图仅owner可读。

文件、原图和快照详情统一 `Cache-Control: private, no-store`；每个Range请求、详情、续期重新鉴权，不返回可绕过后续鉴权的直链。URL中grant是snapshot_grants.id，授权头仍需token匹配。此策略不主动抹除JS已加载画面。原始上传只在磁盘完成态后可引用，清理任务不得删除在途任务引用的文件。

## 6. 上传与删除的数据一致性

原图/GLB上传先保存 files(staged)，持久化完成后改committed才返回inputFileId；任务受理前校验文件归属、用途和committed态。管理员导入经过校验→ready再发布到家具或候选。文件不能在旧资产原地替换。

Storage 完成不等于业务完成；只有确认文件已持久化且渲染检查通过，DB才创建对外ready资产。删除使业务引用与访问资格同事务失效，文件清理由幂等job删除；清理失败保留内部待办且拒绝读取，不展示不可用占位。历史快照保留审计版号但已删除源不能签发新读取。不同用户逻辑资产不按hash合并，物理去重本期不实施。
