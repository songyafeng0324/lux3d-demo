02　创意与问题藏宝阁与个人小屋 · 项目报告书
WHERE IT STARTED

没有这个网站时，路有多长创意起点

“我的网站用户直接上传图片，生成模型放入个人背包，然后可以自己编辑房间，以及分享链接。相当于打通了整个链路。”
—— 产品需求原话（PRD v2.0 第 2 节）

原来：三道坎，每一步都可能劝退普通人

一

找 AI 工具

先要知道有哪些 3D 生成工具、哪个能用、怎么注册。

二

生成模型

学会提交图片、等待、下载文件、处理格式。

三

自己做网站展示

得会开发，才能把模型放进可浏览、可分享的页面。

现在：只做一件事——选一张图

1

上传图片

不用先写名称简介，也不选参数。

2

生成并入包

后台异步生成，进入个人背包即可 3D 预览。

3

布置小屋

古建筑里摆家具与藏品，自动保存。

4

分享链接

免登录只读参观，可随时关闭再重开。

5

投稿展出

审核通过，上藏宝阁公开展位。

关键转折　Lux3D 把“单张图片 → 带 PBR 材质的 3D 模型”变成一次 API 调用，才让“普通人上传一张图”成为可能；剩下要解决的，是让这个结果可靠地交付、有地方可去、能被别人看见。

为什么是“藏宝阁 + 小屋”

公共藏宝阁面向古玩、文物方向，由用户投稿与管理员录入共同供给，是“被认可的展出”。
个人小屋留给手办、游戏角色、日常小物，是“属于自己的陈列”。

两个空间共用同一套背包与行走规则，让“生成的东西”有地方可去，而不只是一个下载链接。

三种角色

游客参观公共藏宝阁；通过有效链接只读参观小屋
注册用户生成、背包、布置小屋、开关分享、投稿与撤回
管理员审核、安排展位、上传官方资产、查看用户与当天调额

完成标准刻意定得很实：只有模型真的进入个人背包并能预览，才算生成成功——模拟或供方“成功”都不算。

04　核心技术藏宝阁与个人小屋 · 项目报告书
FROM ONE IMAGE TO ONE EXHIBIT

一张图，怎样变成可靠交付的藏品Lux3D 接入与生成链路

01

上传与额度

PNG / JPEG / WebP ≤ 10 MiB；每日额度按北京时间 00:00 换日，占用与结算在同一事务。

02

后台 worker 提交

调用 Lux3D 中国区“单图转 3D”（G1-Turbo，GLB，PBR）。提交前先落库并锁定报价。

03

轮询与恢复

供方任务 ID 以字符串无损保存；网页关闭、进程重启后由 worker 接力。

04

下载与校验

用真实 Chrome 渲染检验，三角面 ≤ 35 万，glTF 扩展白名单，同 SHA 落存。

05

入包与网页副本

进入个人背包可预览；worker 另生成约 1/7 体积的网页副本供浏览加载。

四条守住的底线（都有测试或实测证据）

  • 不重复扣费：create 不自动重发；遇到未知结果保留 unknown，只凭原任务的精确证据恢复，绝不按“长得像”的历史任务认领。
  • 失败必退额度：供方成功但本站渲染失败，到期限终结后，原提交日只冲销一次。
  • 成功以交付为准：模型必须真的入包且能在 Chrome 里渲染出来，GLB 头合格或供方回 success 都不算。
  • 不合格要说人话：校验失败原因写进后台上传历史，如“三角面超过 35 万”，不是 MODEL_INVALID。

技术栈

前端 React 19 + Three.js（Vite）· 服务端 Fastify 5 + PostgreSQL · 独立 worker 进程 · 建模 Blender（经 MCP 由 Agent 驱动）· 部署阿里云香港轻量服务器 + Nginx，https://yafeng.fun。

12　工程与性能藏宝阁与个人小屋 · 项目报告书
ENGINEERING · PERFORMANCE

好看之后，要让人能打开公网上线后实测并优化

香港服务器到大陆访客的跨境速度波动很大，13 MB 的 GLB 下载从 0.95 s 到 80 s 不等；上线当天首页第一次打开用了 43 秒。于是把“进入前必须下载的内容”压到最小，并让用户模型走浏览器缓存。

渲染预算

贴图显存约 400 → 55 MB
KTX2光照贴图 JPEG 5.9 → 4.3 MB
帧率固定 DPR 1.5 下约 52–65 FPS，自适应降到 1.0 保 50+
绘制调用约 106 次（含辉光第二次渲染）
办法 1

先显示，再变清晰

GLB 只带 128 px 预览贴图、光照贴图用 256 px 小图，天空图改 WebP（2.11 → 0.32 MB）；进场画面出现后，才下载原尺寸贴图、角色与展品。展品详情改为直接借用场景里已加载的同一份模型，不再等半分钟。

办法 2

用户模型走缓存，且更小

worker 为每个就绪模型生成网页副本（几何量化 + meshopt，贴图转 WebP），约为原文件 1/7，服务器 29 个模型 314.2 → 45.7 MB。撤销权限即失效：每次进入仍走一遍鉴权，只是能看时回 304。

办法 3

让 GPU 少干活

贴图转 KTX2，显存约 400 → 55 MB；摆件 GPU 实例化；掉帧时自适应降低像素密度（1.5 → 1.0）。瓶颈其实在像素填充（16 盏实时点光 + 4× MSAA），不在三角面。

诚实记录

数据要经得起复测

D4 时曾报告“GPU 帧时减半”，交替复测三轮后确认只是单次测量偶然，已更正为 1–9%，测帧方法写进踩坑记录。

一轮迭代怎么走（以 D4 的“二层地毯被拉长”为例）

1

用户实走反馈

二层走廊的地毯花纹被明显拉长，和一楼比例不一致。

2

分析根因

二层地毯宽 2.4 m，却沿用一楼 4 m 宽“每 6 m 重复一次”的设置，纵向被拉长约 1.7 倍。

3

从源头修

重复长度改为“宽度 × 1.5”；一楼仍 6 m，二层 3.6 m。改的是 Blender 脚本，不是补丁。

4

重导出 · 重烘 · 重压

三道导出关口为 0，光照贴图重烘，运行版重压；忘一步单元测试就失败。

5

截图核对 + 记录

两层比例一致；写入进展、决策与踩坑记录，提交前再跑回归与跨模型评审。

15　取舍与踩坑藏宝阁与个人小屋 · 项目报告书
DECISIONS & LESSONS

做对的几个决定，和踩过的几个坑只保留对结果有影响的

决定

旧阁整体推翻，而不是修补

用户实走后给出一句否定。我们没有在旧方块上叠贴图，而是回到根因（尺度、材质体系、碰撞靠手抄），重写设计合同，分 D1–D4 四关逐关确认。代价是两天的重做。

结果　最终 53 万面、25 种材质，导出穿插 0；所有画面和碰撞建在同一份 Blender 源上。
决定

碰撞与模型同源

Blender 脚本一次导出 GLB 和布局 JSON（可走面、碰撞、镜头遮挡、展位分档），网页只跑规则、不写几何，禁止手抄坐标。忘记重烘或重压，单元测试会直接失败。

结果　3 千余个可走面采样点与 GLB 射线 0 不一致；2.77 万个镜头机位 0 穿模。
决定

“成功”只认交付

供方回 success、GLB 头合格都不算；模型要在真 Chrome 里渲染出来、同 SHA 落存、进入背包可预览才算。失败原因必须是人话，直接显示在后台。

结果　AC01–AC51 全部通过；失败任务原提交日只退一次额度。
踩坑

辉光把整幅画面“晃白”

阈值 0.92 时，被灯照到的汉白玉、鎏金、抛光地面一起发光。先抬阈值、再改为“选择性辉光”：只渲染登记过的发光材质，其余压黑。

教训　特效要由“谁允许发光”决定，不由亮度决定；新发光材质必须登记。
踩坑

首页第一次打开 43 秒

首屏 22.55 MB，且香港到大陆速度极不稳定；CDN 因备案暂不可用。办法是先显示再变清晰：128 px 预览贴图先进场，进入后再换原尺寸。

结果　首屏 3.55 MB，5 Mbit/s 下 6.4 s 进场画面。
踩坑

楼梯上跳，脚陷进台阶 16 cm

楼梯碰撞是斜坡而模型是台阶，且侧面能钻进石阶。改为每级台阶一块平面碰撞，可走面视为实心体的顶面，行走和空中移动都不得从侧面进入。

结果　1500 次随机行走不离开可走面；跳着上楼梯不再陷入，已加回归用例。
